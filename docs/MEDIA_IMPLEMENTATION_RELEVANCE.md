# Relevance to an independent browser extension

The strongest reusable idea is a pipeline of **multiple observation sources → provenance-preserving candidates → explicit validation → user-selected delivery**. The APK does not establish that one hook, an ad blocker, or a playable page automatically yields a portable, downloadable stream. This assessment uses the static reconstruction; it is not a tested extension or a current exhaustive browser API feasibility audit.

## Practical foundation

Start with a browser extension for DOM and allowed network metadata observation, candidate UI, site exceptions and user actions. Add a native companion only for capabilities that justify it: a reachable media proxy, receiver protocols, persistent download/resume and container conversion/export. An embedded browser is appropriate when owning WebView/window/network lifecycle is central, but it is a different product and cannot be inferred from stock Chrome extension APIs. A system network filter alone cannot recover arbitrary DOM/player state or preserve browser click semantics.

| Product component | What can be reused conceptually | Required integration / limits |
| --- | --- | --- |
| DOM/player detection | Read currentSrc/src/SOURCE/TRACK; observe dynamic nodes/source changes; optional bounded player adapters | Content scripts need matching host/frame permissions; cross-origin DOM remains restricted. Page APIs can require MAIN-world code and a validated message bridge |
| Network metadata | Observe URL/MIME/redirect/context where APIs deliver them | Chrome MV3 webRequest observation is permission-limited; a callback is not guaranteed for every browser/cache/worker activity. Do not substitute Firefox or older blocking webRequest capabilities |
| Candidate state | Separate source identity, context, confidence, headers and freshness | Partition by profile/private session/tab/document/request; shared URL-only maps and silent equal-merge updates should not be copied |
| Validation | Bounded optional prefix/manifest inspection with visible failures | Fetching is an active operation with authorization, cookies, CORS, expiry and side effects; prefix validity is not playback validity |
| Blob/MSE | Associate blob/player URLs with underlying observed manifests/segments | Blob URLs are document/profile scoped and cannot simply be given to another device. The located Android mechanism is provider-specific; no universal segment recorder established |
| Header/cookie handling | Preserve provenance and choose values for the actual destination | Fetch has forbidden headers/browser-controlled UA/Origin/Cookie rules. An extension cannot promise arbitrary header replay; a companion is outside the browser cookie jar and needs explicit scoped authorization |
| Proxy | Register destinations and rewrite only the necessary HLS/DASH references | Requires a server reachable by the client/receiver, destination-aware credential policy, HTTPS/mixed-content/CORS decisions, range support and linked cancellation. Localhost in a receiver URL addresses the receiver, not the phone/desktop |
| Cast | Adapter selection and direct URL versus proxy decisions | Receiver discovery/load/status/subtitles differ by protocol and device. Native sockets/platform SDKs or a companion may be needed; browser Remote Playback is not a universal replacement |
| Download | Separate original transfer, segment assembly and MP4 export | Browser downloads can save a resource; they do not automatically assemble HLS/DASH or carry all player credentials. Persistent segment processing/export may need a native media stack |
| Remux/transcode | Select per-track container copy versus encoding intentionally | Media3 is an Android stack; an independent desktop implementation needs its own supported library/codecs and resource budgeting. Device-dependent encoding cannot be promised universally |
| Subtitles | Keep original, converted and served variants distinct | Charset, timing, markup/style loss and receiver support must be visible and tested |
| Screen recording | Separate permissioned feature if desired | getDisplayMedia/MediaRecorder or OS capture APIs are a different path, with permissions and device limits. No connected WVC recorder is established here |

## Chrome API boundaries to validate before implementation

Primary API contracts: [content scripts and isolated/main worlds](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts), [chrome.scripting](https://developer.chrome.com/docs/extensions/reference/api/scripting), [webRequest](https://developer.chrome.com/docs/extensions/reference/api/webRequest), [declarativeNetRequest](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest), [downloads](https://developer.chrome.com/docs/extensions/reference/api/downloads), [native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), [incognito](https://developer.chrome.com/docs/extensions/reference/manifest/incognito), and [Fetch forbidden headers](https://fetch.spec.whatwg.org/#forbidden-request-header). These links identify the contracts to check; no online/browser capability test was performed in this audit.

MV3 declarativeNetRequest can block/redirect/modify permitted requests; it is not a general response-body/segment capture API. Chrome's ordinary MV3 extension webRequest is primarily observation, with blocking permission restrictions including enterprise cases. A MAIN-world hook can observe selected page calls but is page-visible, races early code, misses retained original references/workers unless installed there, and can change player behavior. A content script's isolated world does not automatically replace the page's fetch/XHR. Neither a DOM MutationObserver nor an event listener proves the corresponding hook is installed.

The source finding that explicit Cookie survives internal proxy redirects materially affects the design: a companion must reselect credentials for each destination and avoid forwarding Authorization/Cookie to unrelated hosts. Do not copy WVC's static alternate-URL fallback, aliased header maps or browser-cookie assumptions blindly. Header names require case-insensitive handling and Set-Cookie requires separate values. Resume should validate 206/offset/entity continuity, with explicit restart behavior for ignored ranges or changing media.

Cancellation must connect the user action through request/job/stream/file ownership, including failures after headers. Maintain a per-document generation and emit UI changes on useful updates as well as new groups. Own temp files from creation, use finally cleanup and explicit crash scavenging. Separate private-mode work and persistent records; the Android `incognito` download flag does not make its records ephemeral.

## Relationship to strict popup blocking

The earlier [blocking static audit](ANDROID_BLOCKING_STATIC_AUDIT.md) remains a separate workstream. Native WebView window callbacks, temporary child classification and Android service-worker integration are not stock Chrome extension equivalents. Preserving the page's JavaScript/player while suppressing new windows is a browser-control problem; media source detection is useful alongside it but does not supply window-creation authority. This audit did not run or replace the requested Chromium/CDP feasibility investigation, and it does not claim that closing a target after creation prevents scripts or requests.

The most consequential remaining uncertainty for the extension is actual all-frame/worker/cache coverage and page continuity (M02/M05/M09), followed by request context and private isolation (M10–M18/M32–M33), receiver/format interoperability (M19–M24), and safe download/export recovery (M26–M34). iOS native gaps do not block an independent design; they limit what can honestly be attributed to the iOS application.
